A · Auth & Onboarding

A1

Multi-identifier login (username / mobile / email)

🔴 blocks
Design
Login accepts username, mobile, or email + password.
API today
POST /auth/login accepts email only.
Needed
A single identifier field resolving to email / phone / username — POST /auth/login { "identifier", "password" }.
Check existing
Does email already accept a phone/username? Is there a username column?
A2

OTP — email + mobile verification

🔴 blocks
Design
Register → Email OTP → Mobile OTP before submit. (We plan to run these on Firebase client-side; this item is only if you want OTP enforced server-side.)
API today
No OTP endpoint of any kind.
Needed
Either POST /auth/otp/send + POST /auth/otp/verify, or accept Firebase ID tokens on POST /auth/register (email_verified, phone_verified / firebase_id_token) so the server trusts client OTP.
Check existing
verify, otp, 2fa, email/verify, phone/verify, activation.
⟢ Decision needed: OTP via Firebase (client) or backend?
A3

Forgot / reset / change password

🟠 upcoming
Design
"Forgot password?" → reset code → new password; Settings → change password.
API today
None.
Needed
POST /auth/password/forgot, POST /auth/password/reset, POST /auth/password/change.
Check existing
Laravel defaults /forgot-password, /reset-password, password/email.

B · Business Profile (KYC / verified / premium)

B1

Full business-details form (~18 fields)

🔴 blocks
Design
After approval, "Fill Business Details" — address, products, company type, MSME no., logo, social links, description (≤1020), association, tags (5–10), website, etc.
API today
POST /profile accepts only name, bio, phone, avatar.
Needed
Extend POST /profile (or new POST /profile/business) to accept business_name, company_type, msme_number, logo, website, description, association, address/city/state/pincode, products[], tag_ids[], social_links. Return them all on GET /profile.
Check existing
business, company, kyc, onboarding/details.
B2

Verified / Premium badges

🟠 upcoming
Design
Verified badge (after admin approval) + Premium badge (active subscription).
API today
approval_status + subscription object exist; no explicit is_verified.
Needed
is_verified (bool) — or confirm we derive: verified = approval_status==approved, premium = subscription.status==active.
